# PV Studio — 3D performance prototype

Desktop photovoltaic design application, prototype stage. Stack: **Tauri 2** shell, **Rust** core
(model, commands, SQLite), **React 19 + TypeScript** front-end, **three.js / React Three Fiber**
viewport.

The prototype answers one question with measured numbers:

> Can a Tauri 2 + React Three Fiber app display and edit 1,000 and 10,000 solar panels within our
> performance budgets, on both WebView2 (Windows) and WKWebView (macOS)?

**Windows (WebView2): yes**, every budget is met on an integrated GPU. See
[Results](#results). **macOS (WKWebView): not measured yet.** The table is ready for that run.

## Getting started

```sh
pnpm install
pnpm dev                 # tauri dev: Vite on :1420 + the Rust shell
```

In the app, pick **Residential · ~1,000 modules** or **Industrial · ~10,000 modules** in the left
panel. Rust regenerates the synthetic `.pvproj` file in the app data folder and opens it.

| Action | How |
|---|---|
| Orbit / pan / zoom | left drag / right drag / wheel |
| Select | click a module; **Shift+click** adds or removes it |
| Box select | **Shift + right drag**, or the box tool + left drag |
| Move | move tool, then drag a selected module |
| Delete | `Delete` |
| Undo / redo | `Ctrl/Cmd+Z` / `Ctrl/Cmd+Shift+Z` (or `Ctrl+Y`) |
| Performance HUD | gauge button in the toolbar, or `F2` |

## Running the benchmark

Use a **release build**. Dev mode runs unminified React with StrictMode and an unoptimised Rust
binary, so it understates performance.

```sh
pnpm tauri build --no-bundle          # → target/release/pv-studio(.exe)
```

1. Start the release binary. Keep the window at its default size (1440 × 900), visible, on battery
   saver **off**.
2. Open a preset, press `F2`, then **Run benchmark**. It takes about 15 s and runs the same scripted
   sequence every time:
   1. Regenerate and open the project; measure `open_project` call → first rendered frame.
   2. Orbit the camera for 10 s at constant angular speed (one full turn): average FPS, minimum FPS
      (lowest complete 1-second window) and p95 frame time.
   3. Select the first 100 modules of array 0 and drag them by 1 cm over 2 s (below the module gap, so the move passes collision validation), preview only:
      FPS during the drag, and the number of IPC calls made during it (must be 0).
   4. Release: one `MoveModules` command, with the round trip measured in the front-end and the
      apply time reported by Rust; then the time until the statics of the changed fields are
      recomputed on the compute thread (`compute:state` idle).
   5. Undo, then redo: round trips.
3. The JSON report path is shown in the HUD:
   - dev build: `testdata/bench-<preset>-<platform>-<timestamp>.json`
   - release build: `<app data>/benchmarks/` (`%APPDATA%\ch.younergy.pvstudio\benchmarks` on
     Windows, `~/Library/Application Support/ch.younergy.pvstudio/benchmarks` on macOS)

   Copy published reports to `testdata/results/`.

The report contains: preset, module count, instanced mesh count, OS, architecture, build flags,
WebView user agent, GPU renderer string (`WEBGL_debug_renderer_info`), screen size, device pixel
ratio, canvas size, estimated refresh rate, all timings, and a pass/fail per budget.

**WebView memory** is measured outside the page, because `performance.memory` only covers the JS
heap and does not exist in WKWebView. Right after a run:

- **Windows:** sum the private bytes and working sets of the processes under `pv-studio.exe`, for
  example with Task Manager's *Details* tab and the *Commit size* column.
- **macOS:** Activity Monitor → the `com.apple.WebKit.WebContent` and `com.apple.WebKit.GPU`
  processes of PV Studio → *Memory*.

## Results

Measured 2026-11-05 on the release build, with the default window size (canvas 1200 × 1040 px,
DPR 1.25). Reports are in [`testdata/results/`](testdata/results/).

**Windows machine:** Windows 11 Pro, WebView2 156, **Intel Iris Xe Graphics (integrated)**,
display at 60 Hz.

FPS is capped by the 60 Hz display. A budget of "≥ 60" counts as met within 2 % (vsync
quantisation). The raw values are shown below.

| Metric | Budget 1k | Windows 1k | macOS 1k | Budget 10k | Windows 10k | macOS 10k |
|---|---|---|---|---|---|---|
| Orbit FPS, integrated GPU (avg / min, p95 frame) | ≥ 60 | ✅ 59.8 / 58, 18.6 ms | _to do_ | ≥ 30 | ✅ 59.8 / 57, 17.5 ms | _to do_ |
| Draw calls for panels | 1 per array | ✅ 6 meshes = 6 arrays | _to do_ | 1 per array | ✅ 2 meshes = 2 arrays | _to do_ |
| Drag of 100 modules | 60 FPS, 0 IPC | ✅ 59.7 FPS, **0 IPC** | _to do_ | 60 FPS, 0 IPC | ✅ 60.0 FPS, **0 IPC** | _to do_ |
| `MoveModules` round trip (Rust apply) | < 100 ms | ✅ 10.9 ms (1.5 ms) | _to do_ | < 500 ms | ✅ 19.6 ms (1.4 ms) | _to do_ |
| Project open → first frame | < 1 s | ✅ 110 ms | _to do_ | < 3 s | ✅ 124 ms | _to do_ |
| WebView memory, private (working set) | < 400 MB | ✅ 325 MB (527 MB) ⚠️ | _to do_ | < 1 GB | ✅ 348 MB (559 MB) | _to do_ |

Other measurements:

- **Undo / redo round trips:** 1k 12.8 / 9.9 ms; 10k 7.0 / 10.9 ms.
- **Per-frame renderer totals:** 1k 9 draw calls / 20k triangles; 10k 5 draw calls / 202k
  triangles. These include buildings and ground.
- **JS heap:** 9 MB (1k), 15 MB (10k).
- **Worst single frame during the orbit:** about 40 ms, an occasional hitch in both presets. It
  shows in the max frame time but not in p95 or the per-second minimum.

Notes:

- ⚠️ **Memory, 1k.** Private memory (325 MB) is within budget. The *sum of working sets* (527 MB)
  exceeds it, because that sum counts the shared Chromium DLL pages once per process (6 WebView2
  processes). We consider private bytes the relevant figure, but we report both. If the team
  prefers working set as the metric, this budget is **missed** on Windows. The 10k scene costs
  only about 25–30 MB more than the 1k scene, so most of this is the WebView2 runtime's own
  baseline, not the scene data.
- **Dev builds are slower.** Before the static-shadow optimisation, the 10k drag ran at 50 FPS in
  a dev build. That figure is not comparable with the release numbers above.

### API key (C6, 2026-11-11)

The Anthropic API key is entered in **Settings** and kept in the OS credential store (Windows
Credential Manager, macOS Keychain) by `pv-secrets`. It goes in once and never comes out: no
command returns it, the front end only gets a status (source, last four characters). The
`ANTHROPIC_API_KEY` environment variable overrides the stored key. « Test » calls the free
`GET /v1/models`. `e2e/c6-cle-api.mjs` checks the whole path (malformed, revoked and valid keys,
extraction with the stored key, removal) against a local stand-in; `PV_SECRETS_SERVICE` gives
tests their own credential entry so that the user's real key is never touched.

### If a budget is missed (macOS or slower machines)

These options are ordered by expected gain for effort:

1. **Lower the render resolution while the camera moves.** Use DPR 1 during orbit and drag, then
   native DPR when idle (drei's `PerformanceMonitor` / `AdaptiveDpr`). Fill rate scales with pixel
   count, so on a 2× Retina display this cuts fill cost by up to ~4×.
2. **Simpler panels when far away.** Below a few pixels per module, draw one quad per panel
   instead of 20 triangles. That gives about 10× fewer triangles at overview distances.
3. **Shadow casters merged per array.** Cast shadows from one thin box per array instead of one per
   module: about 50× fewer shadow triangles when the shadow map does update. (The static shadow
   map already removes the per-frame shadow pass.)
4. **three.js `WebGPURenderer`.** It reduces CPU-side draw overhead, but WebGPU availability in
   WKWebView depends on the macOS version. Expect a moderate gain here, since the scene already
   uses only a few draw calls.

## Architecture

```text
crates/pv-model   domain types, roof frames (u, v) ↔ ENU, commands + inverses, stress presets
crates/pv-store   SQLite (.pvproj): migrations, command journal (undo/redo), PVS1 binary encoder
crates/pv-geo     2D geometry (polygons, oriented rectangles)
crates/pv-layout  roof outlines, setbacks, module grids, mounting blocks, rails, command validation
crates/pv-statics SIA 261 snow / wind, SIA 260 combinations, load descent, ballast (traced)
crates/pv-graph   generic dependency graph: memoised nodes, early cut-off, cancellation
crates/pv-pipeline project → graph wiring (components, layout, zones, loads, descent, ballast, BOM), compute thread
crates/pv-library  component library (library.sqlite): revisions, search, prices, import, datasheets, proposals
crates/pv-copilot  datasheet extraction with Claude (request / response, no network)
src-tauri         Tauri 2 shell: managed state, commands, model:changed event, bindings export
apps/desktop      React app: shell, viewport3d (instanced panels, editor), perf (HUD, benchmark),
                  workers (box selection), store (Zustand projection), i18n
packages/ui       design tokens (CSS + TS) and base components
packages/locales  fr / en / de messages (ICU) + parity check
```

Key rules, as implemented:

- **Rust owns the model.** React keeps a read-only projection: the summary JSON plus a binary module
  buffer. Every change goes through a serialisable `Command`. Its inverse is computed *before* it
  is applied, and both are journalled in `command_log`. Undo applies the stored inverse; a new
  command truncates the redo branch.
- **Large data travels as binary.** `get_module_buffer` returns a `PVS1` buffer through
  `tauri::ipc::Response`, and the front-end receives an `ArrayBuffer`. After a change, only the
  changed modules are fetched (`get_module_buffer_for`).
- **No React component per panel.** There is one `InstancedMesh` per array. Edits update only the
  touched instance ranges (`addUpdateRange`), and meshes are never rebuilt.
- **Nothing crosses the IPC during a drag.** The preview moves instances on the GPU; pointer-up
  sends exactly one `MoveModules`. If Rust rejects it, the instances roll back and a translated
  toast appears. The benchmark asserts 0 IPC calls during the drag.
- **Click selection without per-panel raycasting.** The ray is intersected with the roof planes
  only, giving roof `(u, v)`; a per-array grid index then finds the module, checking a 3 × 3 cell
  neighbourhood. Box selection runs in a Web Worker on the module centres.
- **Errors are i18n keys plus parameters, never prose.** A Rust test checks that every backend
  error key exists in `en.json`.

## Decisions and deviations from the brief

| Topic | Decision |
|---|---|
| PVS1 record size | **36 bytes**, not 32: the listed fields add up to 36. Agreed with the product owner. |
| tauri-specta | `=2.0.0-rc.26`, the only line that supports Tauri 2 (exact pins, as its docs require). `ts-rs` was not needed. |
| TypeScript | 6.0.3: typescript-eslint 8.72 does not support TypeScript 7 yet. |
| React | 19.3: required by React Three Fiber 9 (the brief allows 18+). |
| Floats in bindings | Exported as `number`, not `number \| null`. Rust never emits non-finite values, and a `NaN` sent from JS is rejected at the IPC boundary. |
| Exact undo of moves | The inverse of `MoveModules` is `SetModulePositions` (exact coordinates), because `(u + du) − du ≠ u` in floating point. Undo is bit-exact. |
| Extra commands | `stress_project_path`, `get_module_buffer_for`, `platform_info`, `write_bench_report`. |
| Stress project files | `create_stress_project` replaces an existing file at the same path, so every run starts from the same state. |
| String index | Stored by Rust (every 18 modules) and not sent in PVS1 (format fixed). The front-end derives it with the same rule (`id / modulesPerString`) for colouring only. |
| kWp | The rating (430 Wp) comes from Rust in the project summary; the front-end only multiplies it by the selection count. |
| Static shadow map | Re-rendered only when the model changes. During a drag preview, the moved modules' shadows update on release. |
| `src-tauri` tests | None: on Windows a Tauri test binary lacks the application manifest and aborts. All logic is tested in `crates/*`. |
| Event permissions | `capabilities/default.json` grants only `core:event:allow-listen` / `allow-unlisten`. |
| Component storage | `library.sqlite` keeps each component as typed JSON with indexed generated columns (no table per family, no translation or manufacturer table: descriptions and manufacturer live in the JSON). |
| Base catalogue ids | Fixed UUIDs (`pv_model::component::presets`): every library, project and future `.pvlib` package names the same base components. |
| Old mounting snapshots | Converted on open into components with content-derived ids (UUID v8), checked to resolve to the same system; the undo journal of such files is cleared (its commands use the old format). |
| Resolution | `MountingNode` in the graph rebuilds the engines' `MountingSystem` from the frozen components; the engines are unchanged. Component references are a separate graph input, so choosing another system does not invalidate the layout nodes. |
| Adoption | A command referring to library components the project lacks is completed in Rust with their closure (one batch, one undo step); components already frozen keep their version until an update proposal is accepted. |
| Variant field names | Fields inside enum variants stay snake_case in JSON (`stock_length_m`, `frame_height`), like the existing `Driver`. |
| Price lists | Read by the front end (exceljs worker, as for the export); recognition, matching and cents in Rust. No new native dependency. |
| Copilot | `pv-copilot` is pure (request and response); the shell sends the request with `reqwest` + native TLS (schannel on Windows). A component the copilot writes is never `verified`. |
| API key storage | OS credential store through `keyring` with explicit platform features (`windows-native`, `apple-native`): without them keyring silently falls back to an in-memory mock. Rejected: `tauri-plugin-store` (plain JSON file), `tauri-plugin-stronghold` (one more password). No plain-text fallback. |

## Out of scope

As specified: map import, photogrammetry, roof detection, layout algorithm, statics, electrical
design, stringing, cabling, simulation, batteries, reports/exports, 2D CAD, copilot, component
library. Only the four workflow steps are shown, and only "Layout" is active.
